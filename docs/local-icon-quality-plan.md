# Local icon quality and memory plan

The item branch in `scripts/local-icons.py` sends the renderer the equipment category, name, description and raw campaign setting. A hat can be in the `helmet` slot, its name can refer to a mapmaker, and its setting can describe a town in a forest. Those are useful clues for designing a hat but poor instructions for painting just the hat. The reported failures fit this prompt; we haven't inspected the images.

1. **Separate the object from its setting.** Use the already-loaded Qwen planner. Cache a short campaign style with colors, materials and finish; give only those fields to the item planner. From the item's own name and description, extract the physical object, silhouette and at most one distinctive construction detail. Treat its equipment slot as a hint. Exclude origin stories, locations, mechanics and text from the resulting caption. Depict a map if the item actually *is* a map; do not turn a mapmaker's profession into a map printed on a hat. If the planning output is malformed, don't send the raw setting to the renderer.
2. **Control composition.** Render the resulting object by itself as painted inventory art, fully within a clean margin on a uniform matte background. For a hat, a useful brief is “One moss-green felt hat with a folded brim and a braided leather band, on plain charcoal.” For a sword, “One narrow steel sword laid diagonally, with a dark leather grip and a brass guard, on plain charcoal.” These are examples, not hardcoded replacements. Keep ability art on its own action-first, character-themed path. Keep all icon art unlettered.
3. **Use a checkpoint with guidance control.** Try [FLUX.2 klein Base 4B](https://huggingface.co/black-forest-labs/FLUX.2-klein-base-4B) in place of the four-step distilled checkpoint. Its published reference uses 50 steps and guidance 4 at 1024 px. This buys control at the cost of longer background jobs; it does not prove better art. Use 4-bit weights, tiled decoding and a single job at a time. Load one image model only. Account for cold start and longer jobs in the icon queue's current five-minute request timeout.
4. **Prioritize system RAM.** Set the PyTorch allocator ceiling before loading weights to at most 7,000,000,000 bytes (6.52 GiB), reduced further when device memory is already occupied. Allow room for Windows, Chrome, the game, CUDA overhead and working tensors. Keep the quantized image transformer on the GPU across requests when there is room; stage the text encoder and decoder by phase without keeping a duplicate CPU transformer. Recheck free memory before generation. Under pressure, defer the image or leave the existing fallback visible instead of retrying with a large host-RAM allocation. Bound both model-loading and generation allocations. The [PyTorch limit](https://docs.pytorch.org/docs/main/generated/torch.cuda.memory.set_per_process_memory_fraction.html) covers its allocator, not total graphics memory or Windows shared GPU memory.
5. **Let the host judge it during normal play.** Log worker RAM, peak allocated and reserved GPU memory, device-wide free memory, placement and generation time. Use the reported 6.43–6.45 GiB steady process RAM as the baseline, and report cold-start memory separately. Version the item and ability caches for the new renderer; leave existing portraits and saved image URLs alone. Review the next hat and sword at the normal card size: each should be recognizable as one object, the campaign expressed through its finish, with no scenery or lettering. No automatic previews, image comparisons or benchmarks.
